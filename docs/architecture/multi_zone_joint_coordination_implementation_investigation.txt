1. VERIFY THE ACTUAL CURRENT MULTI-ZONE ACTION FLOW
====================================================================

Traced fresh from live_perception/building_observation_adapter.py,
rl_training/production/live_inference.py,
rl_training/production/decision_engine.py, and
live_runtime/live_decision_coordinator.py -- not summarized from memory.

  Live fused observations
    -> BuildingObservationAdapter.to_building_observation(fused_observations,
       timestamp, known_zone_ids=...) -> BuildingObservation
       (live_perception/building_observation_adapter.py)
    -> LiveRLInferenceEngine.infer(observation, active_recommendation_by_zone,
       active_broadcast, elapsed_time, max_time, ...) -> InferredRLAction
       (rl_training/production/live_inference.py:260-294) -- internally:
       encodes via PerceptionObservationEncoder.encode(), calls
       self._model.predict(encoded_observation, deterministic=deterministic)
       (ONE forward pass, ONE action_index out), then
       _decode_action(self._action_schema, int(action_index)) ->
       InferredRLAction(action_index, recommended_edge_id, recommendation_label).
    -> RLActionDecisionEngine.set_action(inferred.recommended_edge_id,
       self._rl_engine.zone_ids) (live_runtime/live_rl_decision_pipeline.py:161)
       -- this is where "one action" becomes "N identical per-zone entries":
       set_action() (decision_engine.py:62-65) stores exactly ONE scalar
       (self._recommended_edge_id) plus the full zone_id tuple
       (self._zone_ids); no per-zone differentiation happens here, only
       bookkeeping for what decide() will later broadcast.
    -> LiveDecisionCoordinator.tick(stair_ids, occupant_ids_by_stair,
       covered_stair_ids, timestamp, building_observation=observation)
       (live_runtime/live_decision_coordinator.py:62-111) -- five steps,
       verified by direct re-read:
         Step 1: compute_asset_occupancy_snapshot() for stairs only
           (observable_assets.facts, unmodified).
         Step 2: self._bridge.update_and_publish(asset_observations,
           timestamp, self._decision_engine) -- this internally calls
           self._decision_engine.set_stair_congestion_states(...)
           (a THIRD setter, distinct from set_action()/
           set_zone_recommendations(), never mutually exclusive with
           either -- decision_engine.py:72-82).
         Step 3: observation = building_observation if supplied else an
           empty BuildingObservation() (never fabricated).
         Step 4/5: return self._decision_engine.decide(observation, timestamp).
       LiveDecisionCoordinator.tick() NEVER calls set_action() or
       set_zone_recommendations() itself -- its own docstring
       (live_decision_coordinator.py:26-31) states this explicitly: "it
       is the caller's own separate responsibility to have already
       called that engine's set_action()/set_zone_recommendations()."
       Verified: LiveDecisionCoordinator has no reference to InferredRLAction,
       LiveRLInferenceEngine, or any RL-specific type at all in its own
       import list (live_decision_coordinator.py:1-9) -- it is generic
       over "any object exposing set_stair_congestion_states()/decide()"
       (its own comment, lines 33-36).
    -> RLActionDecisionEngine.decide(observation, time) -> DecisionRecommendation
       (decision_engine.py:290-323).

  QUESTION-BY-QUESTION ANSWERS:

  - What action does one RL inference actually produce? Exactly one
    action_index -> exactly one InferredRLAction(recommended_edge_id,
    recommendation_label) pair. One float-in, one categorical-index-out,
    per model.predict() call. Verified: LiveRLInferenceEngine.infer()
    calls self._model.predict() exactly once (live_inference.py:292),
    no loop, no per-zone call.

  - How does that action become per-zone recommendations? By
    set_action()'s own construction (decision_engine.py:62-65) storing
    one scalar against the FULL zone_id tuple, then decide()
    (lines 294-297) building `effective_actions = {zone_id: self.
    _recommended_edge_id for zone_id in self._zone_ids}` -- a dict
    comprehension that mechanically repeats the same value once per
    zone_id. This is the ONLY step where "per-zone recommendations"
    come into existence at all; it is pure repetition, not derivation.

  - Is the same recommendation truly broadcast to every zone? Yes,
    confirmed at the exact line: decision_engine.py:297,
    `{zone_id: self._recommended_edge_id for zone_id in self._zone_ids}`.
    Every value in that dict is `self._recommended_edge_id`, a single
    Python object reference, for every key.

  - Where does set_zone_recommendations() fit? At the EXACT same call
    site set_action() occupies today: live_runtime/
    live_rl_decision_pipeline.py:161, immediately before
    self._decision_coordinator.tick(...) is invoked. Nothing else in
    tick() needs to know which of the two setters was used.

  - Can it override recommendations per zone without modifying the RL
    policy? Yes, unconditionally. set_zone_recommendations() (decision_
    engine.py:67-70) takes an already-fully-formed
    Mapping[str, Optional[str]] from the CALLER -- it does not read the
    RL policy, does not call infer() again, does not touch
    LiveRLInferenceEngine or the saved model artifact in any way. The
    RL policy has already finished its one forward pass by the time
    this setter is called; nothing here or downstream can cause a
    second inference.

  - Does it override the action entirely, or only affect final
    ZoneRecommendation construction? Precisely the latter, and this
    distinction matters: there is no single stored "the action" object
    for it to override. set_action()/set_zone_recommendations() are
    mutually exclusive INPUT MODES for the one thing decide() actually
    builds -- effective_actions, a plain per-zone dict (decision_
    engine.py:294-297) -- which then feeds _build_zone_recommendation()
    per zone (lines 299-302) to construct ZoneRecommendation objects.
    Calling set_zone_recommendations() after the RL already inferred
    its single target does not "undo" that inference (it already
    happened, upstream, independently, and produced the SAME
    recommended_edge_id the coordinator will read as its starting
    point) -- it only changes which per-zone target string decide()
    uses when it NEXT constructs ZoneRecommendation objects, this tick.
    Confirmed by decide()'s own branch (lines 294-297): whichever setter
    ran last simply determines the source of effective_actions; every
    other line of decide() (severity/occupancy/is_unsafe computation,
    priority ordering, unsafe_zone_ids) is identical regardless of which
    branch supplied it.

2. DEFINE THE EXACT COORDINATION PROBLEM USING CURRENT REPOSITORY CONCEPTS
====================================================================

A. SHARED TARGET OVERLOAD

  "combined expected demand = sum of occupancy estimates for zones
  assigned to the same target" -- can the repository currently compute
  this? NO, confirmed absent (re-verified this session by grepping
  ai_decision/, rl_training/, live_runtime/ for groupby/defaultdict/
  by_target/by_exit/by_stair -- zero matches, matching the prior
  report's own finding). What is missing, precisely: a grouping step
  (zone_id -> target_id, inverted to target_id -> [zone_id, ...]) and a
  summation step over each group's ZoneRecommendation.occupant_count.
  Neither exists. What is NOT missing: the raw per-zone inputs
  (recommended_exit_edge_id, occupant_count) are both already honestly
  present on every ZoneRecommendation object decide() already produces
  -- this is aggregation logic to be added, not new sensing.

B. ROUTE OVERLAP

  Can existing topology/pathfinding infrastructure detect a shared
  corridor/door/stair between two zones with DIFFERENT targets? Traced
  fresh this session from navigation/edge.py and pathfinding/route.py:
  YES, and more completely than either prior report stated -- see the
  correction below.

  CORRECTION TO BOTH PRIOR REPORTS: navigation/edge.py:71-75 defines
  `Edge.EDGE_TYPES = (DOOR, EXIT, STAIR)` -- there is NO "Corridor" edge
  type anywhere in this codebase's NavigationGraph. Every single edge on
  every route, from the first hop to the last, IS one of exactly Door,
  Exit, or Stair (confirmed: navigation/graph_builder.py only ever adds
  edges derived from Door.zone_a_id/zone_b_id, Exit.zone_id, or a
  Staircase's floor-to-floor references -- no other edge-producing
  object exists in the Building model). The prior reports' claim that "a
  shared plain-corridor edge has no capacity concept" was based on an
  incorrect assumption that a generic Corridor edge type exists; it does
  not. This means shared-edge detection via Route.edge_ids intersection
  (pathfinding/route.py:46-48) is potentially capacity-actionable on
  EVERY shared edge along a route, not merely on a route's final target
  edge -- see Section 5 for the capacity-number confirmation that makes
  this concrete, not merely structural.

  Mechanism: Route.edge_ids is a plain list; PathfindingEngine.
  nearest_exit()/dijkstra()/alternative_paths() (pathfinding/engine.py)
  already return full Route objects with every intermediate edge
  populated -- comparing two zones' edge_ids lists for intersection uses
  nothing not already returned by an existing, unmodified query.

C. STAIR CONGESTION INTERACTION

  Re-traced stair_congestion/predictor.py fully this session (not
  assumed): StairCongestionPredictor.observe() (lines 102-206) takes a
  bare (stair_id, timestamp, occupancy) triple and has, per its own
  module docstring (lines 10-29), "no opinion about, and no access to,
  WHERE that occupancy number came from." Its trend/prediction
  (_predict(), lines 210-228) is a deterministic linear extrapolation of
  PAST observed samples only (rate computed from a rolling window,
  lines 138-185) -- there is no parameter, field, or call path anywhere
  in this module through which "N zones with combined occupant_count M
  were just assigned this stair" could be communicated to it. This is
  proven by the module's own signature, not inferred from naming.

  "already congested" vs. "expected to become congested because the
  coordinator assigns multiple zones there" -- these are genuinely
  different facts in this codebase and must stay genuinely separate:
    - "already congested" = StairCongestionState.current_occupancy /
      currently_exceeds_threshold -- a real, perception-derived,
      CURRENT-cycle-only fact (stair_congestion/models.py:59-78, "every
      Optional[...] field is None... whenever status is UNKNOWN for THIS
      cycle -- this type requires a genuine current-cycle reading to
      report anything at all").
    - "expected to become congested because of this recommendation" =
      NOT a value the predictor can ever produce, because it never
      receives the coordinator's own decision as an input. This can only
      be computed BY the coordinator itself, as new aggregation logic
      (Section 2A), never retrieved from StairCongestionPredictor.
  StairCongestionState CAN be used as coordination evidence, but only
  as INFORMATIONAL/soft evidence (a tie-breaker among already-necessary
  alternates, or a hedged note) -- never as a hard constraint that
  excludes a target on its own, because it has zero awareness of the
  very demand the coordinator's own decision is about to create. Its
  authority is not changed by this report: it remains exactly the
  "monitor, never decide" role RLActionDecisionEngine._stair_congestion_
  note() already gives it (decision_engine.py:152-207).

D. CONTRADICTORY RECOMMENDATIONS -- precise definitions, not vague language

  - Two zones assigned to the same exit: NOT, by itself, contradictory
    -- it is only a CONFLICT (a fact requiring a decision) once combined
    demand for that exit, honestly summed (Section 2A), is compared
    against that exit's real capacity (Section 5) and found to exceed
    it. Two low-occupancy zones sharing a large exit is not a conflict
    at all under this definition; the repository provides no basis for
    calling it one without the demand/capacity comparison actually being
    run.
  - Two zones assigned to routes sharing a corridor: reframe per the
    2B correction -- "corridor" in this codebase's own vocabulary means
    a sequence of Door/Exit/Stair edges. This is a conflict under the
    SAME definition as above, evaluated per shared edge rather than per
    final target: only a conflict once summed demand crossing that
    specific shared edge exceeds that edge's own capacity.
  - One zone told to use a stair while another is told to use a door
    connected to that same stair: this is well-defined and checkable --
    "connected to that same stair" means the door's edge appears in a
    route that also traverses the stair edge (or the door IS the stair's
    own approach edge). It is a conflict under the identical
    demand-vs-capacity test, applied to the STAIR edge specifically
    (since climbing the stair is what both zones would actually share,
    even though their nominal "target" strings differ) -- again, only
    once the summed demand across BOTH zones' contribution to that
    shared stair edge is checked against the stair's own capacity, never
    merely because the two target strings differ.
  - Two recommendations causing aggregate demand beyond some known
    capacity: this IS the repository-provable definition of "conflict"
    this report adopts throughout -- restated as the single, precise
    rule: a conflict exists at edge E if and only if the sum of
    occupant_count over every zone whose route to its own assigned
    target passes through E exceeds a real capacity number for E
    (Section 5). Nothing else in this codebase provides an evidentiary
    basis for calling a set of recommendations "contradictory" -- shared
    target strings alone, shared route strings alone, or a stair merely
    being RISING alone are all, individually, insufficient evidence
    under this report's own standard (Section 2C).

4. DEMAND ESTIMATION HONESTY -- signal classification
====================================================================

Every signal a coordinator could reach for, classified precisely
against source (re-verified this session, perception/models/
building_observation.py and live_occupants/ read directly):

  estimated_occupancy (BuildingObservation.occupancy_observation(zone_id)
  .estimated_count)
    Classification: ESTIMATED. Optional[float]; None means "no reading
    this cycle," a non-None value (including 0.0) means a real sensor-
    derived estimate, possibly a genuine zero. (perception/models/
    building_observation.py:73-83, "estimated_count follows...
    convention exactly: None means no reading available, never zero
    people.")

  confidence (ObservedOccupancy.confidence)
    Classification: ESTIMATED, when present; UNKNOWN (None) otherwise.
    Same dataclass, same file, line 83 -- Optional[float], no default
    other than None.

  observation_state / ObservationState (per zone, hazard side --
  distinct mapping from occupancy)
    Classification: OBSERVED or UNOBSERVED, an explicit two-value enum
    (building_observation.py:10-26) -- never inferred from whether
    another field happens to be None. This is the one field in this
    type that is NOT itself an estimate; it is a coverage flag.

  missing/unknown zones (a zone_id entirely absent from
  BuildingObservation's internal mappings)
    Classification: UNKNOWN, and (important, re-verified this session)
    INDISTINGUISHABLE from "covered but produced no reading." Both
    node_observation()/occupancy_observation() are TOTAL accessors
    (building_observation.py:213-221) that return a fresh, all-default
    object for any id not present in the mapping -- the SAME value a
    genuinely-covered-but-empty reading would produce. This is an
    existing, disclosed limitation of BuildingObservation itself; no
    coordinator design can distinguish these two cases from this type
    alone.

  confirmed zero vs. unknown
    Classification: this codebase supports exactly ONE honest
    distinction here -- estimated_count is None (UNKNOWN) vs.
    estimated_count is a real float including 0.0 (ESTIMATED, possibly
    a genuine zero reading). There is no separate "confirmed zero"
    representation stronger than an ordinary 0.0 estimate; a coordinator
    must not claim more certainty for a 0.0 reading than any other
    estimate carries.

  any live occupancy structures (live_occupants.LiveOccupant /
  LiveOccupantManager -- real position-tracked occupants, the
  canonical live occupancy source used by CrowdIntelligenceEngine)
    Classification: ESTIMATED (genuinely real, perception-derived, NOT
    simulator ground truth) but NOT CURRENTLY REACHABLE from this
    pipeline without new wiring this task explicitly forbids --
    LiveOccupantManager is constructed only inside LiveOrchestrator's
    own composition (live_runtime/factory.py), never inside
    LiveRLInferenceEngine/LiveRLDecisionPipeline/LiveDecisionCoordinator
    (verified: none of those three files import live_occupants or
    construct a LiveOccupantManager). This is a distinct bucket from
    both "UNKNOWN" and "PRIVILEGED" -- it is real and honest, just
    architecturally out of reach for THIS coordinator under this task's
    own constraints. Not proposed as an input here.

  HazardSnapshot / OccupancySnapshot / any Ground-Truth-shaped type read
  independently of perception
    Classification: PRIVILEGED / MUST NOT USE. Confirmed by every
    existing GroundTruthIndependenceTests-style guard already covering
    this pipeline's neighboring files (e.g. rl_training/production/
    decision_engine.py's own forbidden-import test extends this exact
    idea to pathfinding/navigation too). A coordinator must construct
    its OWN hazard_snapshot_from_observation()-derived HazardSnapshot
    (ai_decision/perception_adapter.py:109-128, itself perception-
    honest, built only from BuildingObservation) if it needs one for
    hazard-aware routing (Section 6) -- never read a hazard_provider or
    a simulator-produced snapshot directly.

  HOW UNKNOWN SHOULD AFFECT ALLOCATION: a zone with estimated_count=None
  MUST NOT be summed as 0 in any demand total -- this is the SAME
  finding the readiness report already made (its Section F), re-
  confirmed this session against the same source, and restated here
  precisely: it is unsafe specifically because a capacity comparison
  built on a demand total that silently dropped a real (if unmeasured)
  population would look "under capacity" only because evidence was
  discarded, not because demand was actually low. A coordinator must
  carry an explicit "N zones contributing to this target have no
  occupancy reading this cycle" count alongside any numeric demand
  total. If reliable demand cannot be determined for a zone (its own
  estimate is None), the coordinator must not invent a number for it --
  it should still be assigned a real target (routing is separate from
  demand accounting, Section 6), but its contribution to whether a
  redistribution trigger fires should be treated as an honest unknown,
  not a zero and not an assumed-average value.

  evidence (Sections 2, 4, 5) sufficient to justify a bounded override,

  unaddressed. Model A is not "safer" here; it is strictly weaker than
  what the evidence supports.

  Model C (independent allocator, every zone assigned independently to
  its own optimal route): REJECTED. This would silently replace the RL
  policy's own whole-building, hazard/occupancy-informed judgment (its
  observation genuinely includes every zone's hazard/occupancy state,

    - What information allows an override: a per-edge demand total

8. THE "TWO-ZONE SAME TARGET" SCENARIO, ARCHITECTURALLY
====================================================================

  RL preferred target: Stair S1
  Zone A -> S1
  Zone B -> S1 initially
  Coordinator detects a justified conflict
  Final: Zone A -> S1, Zone B -> alternative feasible target

  Where would the alternative come from? PathfindingEngine.distances_from(
  zone_B_node_id) (pathfinding/engine.py:234-270, already exists,
  unmodified) -- a single-source search returning a Route to EVERY node
  Zone B can reach, filtered to Exit/Stair-type goal nodes excluding S1,
  picking the lowest total_cost candidate. This reuses one existing
  method call; no new search algorithm.

  How would route feasibility be checked? The SAME hazard-aware
  PathfindingEngine (Section 3/6) used to compute Zone A's and Zone B's
  original routes to S1 in the first place -- built once per tick from
  hazard_snapshot_from_observation(observation) + HazardAwareCostModel,
  both already perception-honest and already proven in production by
  AIDecisionEngine. An edge the perception layer flags blocked_estimate=True
  costs HazardAwareCostModel.BLOCKED_COST (effectively infinite) and is
  never selected -- the alternate is only ever a route the SAME hazard
  evidence considers real.

  How would UNKNOWN occupancy affect redistribution? If Zone B's own
  occupant_count is None, Zone B is STILL eligible to be the one
  redirected (routing does not require a known headcount, Section 4) --
  but Zone B's own unknown contribution must not be what TRIGGERED the
  conflict determination in the first place if the comparison as a
  whole becomes unreliable (Section 6's abstention rule); if Zone A's
  known occupant_count alone already exceeds S1's capacity, the
  conflict is real regardless of Zone B's unknown status, and Zone B
  (or Zone A) may still be redirected -- the tie-break (below) does not
  depend on knowing Zone B's headcount to decide WHICH zone moves, only
  on knowing that a move is honestly justified at all.

  How would the coordinator avoid arbitrarily choosing Zone A over Zone
  B? By a stated, deterministic, disclosed-as-placeholder rule -- this
  report proposes (not implements) the smallest defensible one: redirect
  the zone(s) FARTHEST from S1 first (highest total_cost to reach S1,
  as already computed by the same PathfindingEngine search both zones'
  original routes came from), keeping S1 assigned to whichever zone(s)
  are already closest to/most committed to it. This is explicitly the
  SAME honesty level ai_decision.priority.SeverityOccupancyPriorityRule
  already discloses for its own V1 ranking ("a documented placeholder,
  not a validated life-safety prioritization model") -- not presented as
  optimal, only as deterministic and explainable.

  What deterministic rule could be used for tie-breaking (equal
  distance)? zone_id, lexicographic -- the SAME final tie-break
  ai_decision.priority.severity_sort_key/SeverityOccupancyPriorityRule
  and RLActionDecisionEngine._priority_evacuation_order() already both
  use ("...then zone_id for full determinism when both are tied,"
  ai_decision/priority.py:65-71) -- reused, not invented, for exactly
  the same "must never be ambiguous" reason.

9. SAFETY AND UNKNOWN-DATA BEHAVIOR
====================================================================

  UNKNOWN zone occupancy: routed normally; excluded (as an honest
  unknown, not zero) from demand totals; can still trigger abstention
  if it makes a comparison unreliable (Section 6). Never treated as
  safe, never treated as "must redirect."

  UNKNOWN hazard (a zone's node_observation not OBSERVED this cycle):
  unchanged from today's existing, independently-computed
  is_unsafe/severity logic in RLActionDecisionEngine
  (_build_zone_recommendation(), decision_engine.py:99-150) -- UNKNOWN
  severity already conservatively resolves to is_unsafe=True there,
  completely independent of and unaffected by whatever target the
  coordinator assigns. A coordinator never overrides or duplicates this
  judgment.

  UNKNOWN route information (a hazard-aware search returns no Route at
  all, from ANY node to ANY candidate target): the coordinator abstains
  for that specific zone -- keeps the RL's original target unchanged,
  the same behavior as today (Section 6), never fabricates a route.

  No alternative target: same as above -- abstain, keep original.

  No path to alternative target: identical case to "no alternative
  target" -- there is no meaningful distinction in this codebase between
  "no candidate exists" and "a candidate exists but is unreachable";
  both collapse to PathfindingEngine returning no usable Route.

  Current stair congestion UNKNOWN (StairCongestionState.status !=
  OBSERVED for this cycle): the informational note mechanism already
  returns None/nothing in this case
  (RLActionDecisionEngine._stair_congestion_note(), decision_engine.py:
  178-183, "state.status != ObservationStatus.OBSERVED: return None") --
  a coordinator's OWN soft tie-breaker use of this signal (Section 2C)
  must follow the identical discipline: an UNKNOWN congestion state
  contributes nothing, positive or negative, to a redistribution
  decision. It must never be treated as "safe to send more people
  there" nor as "must avoid."

  Conflicting topology information: not found as a real possibility in
  this codebase -- NavigationGraphGenerator builds one deterministic
  graph per Building per construction (Section 3); there is no
  mechanism by which two different graph reads within one tick could
  disagree, since the coordinator would hold exactly one already-built
  graph, constructed once. This scenario is disclosed as "not
  applicable given this architecture," not silently skipped.

  Governing principle, restated precisely: every branch above resolves
  to either (a) act, using a repository-provable fact (Sections 2, 5),
  or (b) abstain, preserving the RL's original broadcast value
  unchanged. There is no third branch anywhere in this design that
  fabricates a route, a capacity number, a safety claim, or an
  occupancy count. UNKNOWN is never silently promoted to "safe," and is
  never silently promoted to "must redirect everyone" either -- both
  would be equally dishonest, and this report rejects both.
