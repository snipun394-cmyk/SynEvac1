2.1 RootCauseReproductionTests::test_chain_topology_with_every_zone_occupied_produces_navigation_rejections
-----------------------------------------------------
File: tests/test_campaign_diagnostics.py

Behavioral assumption that changed: the test previously assumed the
5-zone chain / every-zone-occupied / unconstrained-fire fixture would
run generation and produce SOME rejected candidates
(`self.assertGreater(summary.rejected, 0)`), with the fixture's own
comment noting it deliberately did not assert a specific ratio "since
it depends on exactly which zone gets sampled as ignition each
attempt."

Why the old expectation is no longer correct: with Phase 1 in place,
zone-1 (the zone farthest from the Exit in this chain) is provably
optimistic_reachable=True but has its ENTIRE fire-eligible zone set
classified LETHAL (every other zone in the chain sits on its only path
out), giving lethal_fire_probability=1.0 -- a Case 2 blocking ERROR.
The campaign is now stopped at pre-flight, before the per-scenario loop
ever runs, so `summary.rejected` is 0, not "some positive number
depending on the sampled ignition zone" -- there is no longer any
per-attempt sampling to depend on.

New assertions (strictly more, not fewer):
  self.assertTrue(preflights[0].has_errors)
  self.assertTrue(preflights[0].feasibility_issues)
  self.assertEqual(summary.accepted, 0)
  self.assertEqual(summary.rejected, 0)
  self.assertIn("proven infeasible", summary.rejection_explanation)
  self.assertIn("zone-1", summary.rejection_explanation)

Confirmed not weakened in any other way: the OLD single assertion
(`rejected > 0`) checked only that SOME rejection happened, with no
attribution to WHICH zone or WHY. The NEW six assertions check the
blocking preflight fired, that it specifically carries a FEASIBILITY
issue, that both accepted and rejected are exactly 0 (a stronger, more
specific claim than "rejected > 0"), and that the explanation text
names both the infeasibility proof and the specific zone (zone-1) --
strictly more specific and strictly more verified than before. Nothing
that the old test verified is left unverified by the new one; the
old claim ("this fixture produces rejections, attributed to the right
category") is a strict subset of what the new test now checks (this
fixture is now caught even earlier, and the new test proves exactly
that, by name).

2.2 PerCandidateCaptureTests::test_rejection_explanation_populated_when_every_scenario_is_rejected
-----------------------------------------------------
File: tests/test_campaign_diagnostics.py

Behavioral assumption that changed: the test previously assumed a
2-zone chain with door-1 permanently LOCKED (FixedValue, zero sampling
uncertainty) and fire constrained to zone-1 would run 3 full generation
attempts, each individually rejected at the scenario_validator level,
producing `summary.rejected == 3` and a NAVIGATION-categorized
explanation (`self.assertIn("NAVIGATION", ...)`).

Why the old expectation is no longer correct: door-1 being pinned
LOCKED with NO distribution uncertainty at all means zone-1 is
unreachable even under the OPTIMISTIC bound -- a Case 1
(ZONE_UNREACHABLE_OPTIMISTIC) blocking ERROR, detected before the first
generation attempt. `summary.rejected` is now 0 (nothing was ever
attempted, so nothing could be rejected at the per-candidate level),
not 3, and the explanation now carries the FEASIBILITY-specific code
ZONE_UNREACHABLE_OPTIMISTIC rather than the per-candidate NAVIGATION
category, because no per-candidate validation ever ran.

New assertions:
  self.assertTrue(preflights[0].has_errors)
  self.assertTrue(preflights[0].feasibility_issues)
  self.assertEqual(summary.accepted, 0)
  self.assertEqual(summary.rejected, 0)                    [was: == 3]
  self.assertIsNotNone(summary.rejection_explanation)
  self.assertIn("ZONE_UNREACHABLE_OPTIMISTIC", ...)         [replaces "NAVIGATION"]
  self.assertIn("proven infeasible", ...)

Confirmed not weakened in any other way: the ONE assertion that changed
value (`rejected 3 -> 0`) and the ONE assertion whose substring changed
(`"NAVIGATION" -> "ZONE_UNREACHABLE_OPTIMISTIC"`) both changed because
the thing they were checking (a per-candidate NAVIGATION rejection)
genuinely no longer happens for this fixture -- not because the
assertion was inconvenient, but because Phase 1 legitimately moved the
detection point earlier, past where that per-candidate event could ever
occur. Two NEW assertions were added (preflight has_errors,
feasibility_issues non-empty) that did not exist before -- strictly
more coverage, not less. The underlying scenario_validator-level
NAVIGATION rejection behavior this test used to exercise indirectly
(via a wasted CampaignWorker attempt) remains independently,
unchanged-ly covered by tests/test_scenario_validator.py directly, and
by RootCauseReproductionTests::test_longer_chain_makes_navigation_the_dominant_rejection_reason
(same file), which calls generate_scenario()/validate() directly and
was NOT touched by this diff -- confirmed by `git diff` showing no
change in that test's own body.
