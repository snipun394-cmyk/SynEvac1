1. ACTUAL OCCUPANT SAMPLING ARCHITECTURE DISCOVERED
=====================================================

Traced fresh from the current code this task (not assumed from prior
reports' summaries):

[FACT] scenario_generator/generator.py::_generate_occupant_placements()
iterates `sorted(definition.occupant.occupancy_distribution.items())`
and, PER ZONE KEY, sequentially:
  1. `raw_count = sample(distribution, occupant_rng)` -- one draw from
     the zone's own declared Distribution, using the SAME
     `occupant_rng` stream across every zone key in this one attempt
     (a single `category_rng(attempt_seed, "occupant")` call per
     attempt, re-confirmed unchanged).
  2. `count = max(0, int(round(raw_count)))` -- the exact rounding
     rule Phase 2B's `_p_zero_occupancy()` mirrors precisely.
  3. For `index in range(count)`: `x = occupant_rng.uniform(zone.x,
     zone.x + zone.width)`, `y = occupant_rng.uniform(zone.y,
     zone.y + zone.height)` -- CONTINUOUS position, drawn
     unconditionally, with NO Distribution-based control anywhere in
     the schema (re-confirmed: `scenario_definition.occupant_
     definition.OccupantDefinition` has no position-related field at
     all).

[FACT] No global total-population budget exists anywhere in this
function or elsewhere in `generator.py` -- each zone key's own count is
sampled entirely independently from its own distribution; there is no
"sample a total, then distribute" step. Case D ("global total occupancy
constraints") from the task's own list is CONFIRMED ABSENT from the
current Generator.

[FACT] Zone occupancy counts ARE independent between zones, in exactly
the same sense already established and relied upon throughout this
thread for door/exit/stair objects sharing one category stream:
different zone keys' `sample()` calls are SEQUENTIAL draws from the
SAME seeded `occupant_rng` (not separately-seeded streams, so not
independent in the strongest cryptographic-hash sense), but each call
consumes a bounded, non-overlapping, non-rejection-based amount of
randomness -- independent in the standard-PRNG sense every other
probability calculation in this codebase already depends on.

[FACT, re-verified directly this task] `Zone.contains(x, y)` (models/
zone.py) checks `self.x <= x <= self.x+width and self.y <= y <=
self.y+height` -- an EXACT match to the bounds
`occupant_rng.uniform(zone.x, zone.x+zone.width)` can ever produce.
`scenario_validator.occupant_validation.py`'s own `OCCUPANT_OUTSIDE_
ZONE` (GEOMETRY) check can therefore never fail under legitimate
sampling -- confirmed by direct comparison of the two formulas, not
merely re-cited from the Phase 2 investigation's own prior finding.

[FACT] `scenario_validator.navigation_validation.py::_occupied_zone_
ids(candidate)` reads ONLY `occupant.zone_id` -- `occupant.position` is
never read anywhere in the navigation-relevant validation path.
Combined with the GEOMETRY finding above, this confirms: for candidate
VALIDITY purposes, an occupant's continuous position is provably
irrelevant -- only WHICH ZONE (and whether that zone has >=1 occupant
at all) ever matters. This module therefore never enumerates,
discretizes, or approximates continuous positions anywhere -- there is
no position-related code in `exact_validity.py` at all.


2. WHICH OCCUPANCY RANDOMNESS AFFECTS VALIDATION
=====================================================

[FACT] Exactly one occupancy fact affects NAVIGATION validity: whether
a given zone ends up with >=1 occupant this attempt (a Bernoulli-like
reduction of the zone's own count distribution). Occupant COUNT beyond
"zero vs. at least one," occupant IDENTITY, occupant ORDER, and
occupant POSITION are all provably irrelevant (Section 1).

[FACT, re-confirmed, matching the Phase 2 investigation's own finding]
`OCCUPANT_COUNT_OUT_OF_SUPPORT` (OCCUPANCY category) and
`BEHAVIOUR_PROFILE_...` checks are UNRELATED to navigation and remain
out of this phase's scope, exactly as Phase 2A already disclosed for
the other five non-navigation validator categories.


3. THE MATHEMATICAL MODEL IMPLEMENTED
=====================================================

For one fixed engineering-state combination (a specific fire zone plus
a specific resolved door/exit/stair state vector -- exactly what Phase
2A already enumerates), let every zone with a stated occupancy
distribution be classified SAFE or UNSAFE using the SAME two checks
`navigation_validation.py` itself applies (re-derived, not
re-implemented differently):
  - UNSAFE if the zone is not reachable from Outside under this
    combination with NO exclusion (check 1, NO_EVACUATION_ROUTE), OR
  - UNSAFE if the zone (other than the fire zone itself) is not
    reachable with the fire zone excluded (check 2,
    FIRE_ORIGIN_BLOCKS_EVACUATION).
  - Otherwise SAFE.

[PROVEN, not assumed] A candidate is NAVIGATION-valid under this
combination if and only if every UNSAFE zone receives exactly zero
occupants -- a SAFE zone's occupancy, whatever it is, never causes a
rejection. Since zone occupancy counts are independent (Section 1),
this event's probability is the PRODUCT of each UNSAFE zone's own exact
P(zero) -- call this `p_U`. No Cartesian product over occupant-count
VECTORS is ever needed; this is a closed-form product over a SET
membership test, computed once per engineering-state combination.

[PROVEN] Accounting additionally for `min_open_exits` (kept UNCHANGED
from Phase 2A, per the task's own explicit instruction -- Section 6),
which is only NAVIGATION-active when at least one occupant is present
anywhere (`validate_navigation()`'s own early return): let `p_R` be the
product of P(zero) over the SAFE zones (i.e. the probability that
NO ONE shows up anywhere, `p_U x p_R`, since U and R partition every
occupancy-relevant zone). The exact per-combination formula, derived
in full (not guessed) and implemented verbatim:

    if egress_ok:
        P(valid | combination) = p_U
    else:
        P(valid | combination) = p_U * p_R * (1 if structural_ok else 0)

where `egress_ok` and `structural_ok` are the SAME two facts Phase 2A
already computes for `min_open_exits` (Section 6). This reduces to
Phase 2A's own old binary (0 or 1) behavior exactly whenever every
analyzed zone is guaranteed-occupied (a guaranteed zone's P(zero) is
always 0.0, forcing `p_U` to 0 the instant any guaranteed zone is
UNSAFE) -- Phase 2B is a strict mathematical generalization of Phase
2A, not a replacement, confirmed by the full, unmodified Phase 2A test
suite passing unchanged against the new code (Section 12).


4. HOW CONDITIONAL OCCUPANCY PROBABILITY IS COMBINED WITH
ENGINEERING-STATE PROBABILITY
=====================================================

For each enumerated (fire-branch, engineering-state-combination) pair
(the SAME enumeration loop Phase 2A already runs, extended in place,
never duplicated):
  `weight = combo_probability * branch_weight` (Phase 2A's own,
  unchanged engineering-state probability)
  `valid_weight += weight * combo_occupancy_factor`
  `invalid_weight += weight * (1.0 - combo_occupancy_factor)`

This is exactly the decomposition the task itself proposed
(`Σ P(engineering state) × P(valid occupancy | engineering state)`),
now VERIFIED (not merely assumed) safe to apply, because: (a) fire/
door/exit/stair sampling and occupant-count sampling draw from
disjoint category RNG streams (`"fire"`, `"door"`, `"exit"`, `"stair"`
vs. `"occupant"` -- proven independent in the Phase 2 investigation's
own Section 1.3, re-confirmed unchanged this task), and (b) the
per-combination occupancy factor derived in Section 3 is itself an
exact, closed-form conditional probability given that fixed engineering
state -- so the sum-of-products IS the correct total probability, not
an approximation.

A single engineering-state combination's contribution to `p_valid` can
now be genuinely FRACTIONAL (between 0 and 1) whenever occupancy
uncertainty is present -- `CandidateValidityResult.valid_states`/
`invalid_states` only count combinations whose occupancy factor is
(within floating-point tolerance) exactly 1.0 or exactly 0.0; a
fractional combination is counted in `total_states_considered` but in
NEITHER bucket. This is documented explicitly in the result model's
own updated docstring, so `valid_states + invalid_states <=
total_states_considered` (equality exactly when no analyzed zone has
genuine occupancy uncertainty).


5. PROVEN INDEPENDENCE ASSUMPTIONS
=====================================================

- Occupant counts across DIFFERENT zones: independent (Section 1,
  sequential-draw-from-one-stream argument, the same tier of
  independence this whole thread has consistently relied on for door/
  exit/stair objects within one category).
- Occupant-count sampling vs. fire/door/exit/stair sampling: independent
  (disjoint category RNG streams, the strongest, cryptographic-hash-
  derived tier of independence, re-confirmed unchanged from the Phase 2
  investigation).
- Occupant position vs. anything relevant to validity: IRRELEVANT
  (Section 1) -- not an independence claim at all, a relevance claim,
  proven directly by comparing `Zone.contains()`'s formula to the
  Generator's own sampling bounds and by confirming `_occupied_zone_
  ids()` never reads `position`.


6. DEPENDENCIES DISCOVERED
=====================================================

- `min_open_exits`'s NAVIGATION-based (egress-reachable) check depends
  on WHICH SPECIFIC zones end up occupied, not merely "is anyone
  present" -- a genuine, real complication this task investigated in
  full before deciding how to handle it. The task's own explicit
  instruction ("Keep the Phase 2A handling intact... without changing
  it") was followed literally: `egress_ok` is computed exactly as
  Phase 2A already computes it (using `guaranteed_zones` only, the
  deterministically-always-occupied zones). This is EXACT whenever no
  uncertain-occupancy zone lies in the SAFE set (the common case, and
  every test case constructed for this phase) -- when an uncertain
  zone IS in the SAFE set and `min_open_exits > 0`, its own possible
  presence could in principle contribute additional reachable egress
  capacity beyond what `guaranteed_zones` alone provides; this specific
  refinement was deliberately NOT modeled in Phase 2B (an honest,
  disclosed simplification, not a silent gap -- see Section 8), exactly
  matching the task's own instruction to leave `min_open_exits`
  unchanged rather than extending it.
- The STRUCTURAL (unconditional) vs. NAVIGATION (occupancy-gated)
  min_open_exits split, and the proof that the NAVIGATION check always
  subsumes the STRUCTURAL one whenever occupants exist -- carried over
  unchanged from Phase 2A (Section 6 there), still correctly applied
  here since it does not depend on occupancy uncertainty at all, only
  on whether ANY occupant is present, which Phase 2B's own `p_U`/`p_R`
  split already accounts for via the `egress_ok`/`structural_ok`
  branching (Section 3).

Not handled at all, by design and by proof -- Section 1 shows position

8. OCCUPANCY SIMPLIFICATIONS, AND PROOF THEY PRESERVE VALIDATOR
SEMANTICS
=====================================================

1. Collapsing "does the zone get >=1 occupant" instead of enumerating
   the full count distribution: PROVEN in Section 3 -- validity depends
   only on the zero-vs-nonzero event, so the full count distribution
   carries no additional information relevant to validity. This is not
   an approximation; the exact P(zero) IS the exact information needed.
2. Computing P(zero) analytically for FixedValue, WeightedOptions, and
   (new in this phase) both discrete and continuous UniformRange --
   PROVEN exact for each case in `_p_zero_occupancy()`'s own inline
   derivation (a closed-form weight-sum or interval-length-ratio
   calculation, never a sampled estimate). Continuous UniformRange's
   P(zero) is computed as the exact length of the sub-interval below
   the rounding boundary (0.5) divided by the total interval length --
   an exact calculation for a continuous uniform distribution, not an
   approximation, because a UNIFORM continuous distribution's
   probability over any sub-interval is exactly proportional to that
   sub-interval's length by definition.
3. Keeping `min_open_exits`'s egress check scoped to `guaranteed_zones`
   only, unchanged from Phase 2A: NOT claimed to be exact in every
   case -- disclosed honestly in Section 6 as a deliberate, task-
   instructed simplification with a known (narrow) blind spot, not
   silently assumed correct.
4. Fire-origin LETHAL/SAFE pruning kept scoped to `guaranteed_zones`
   only: PROVEN still sound as a PRUNING criterion (not a probability
   claim) -- if a fire zone disconnects a guaranteed zone, the WHOLE
   branch is invalid regardless of what happens to any uncertain zone,
   since the guaranteed zone's own occupants (who are certainly
   present) cannot escape either way. Uncertain zones' fate under that
   SAME fire zone is irrelevant once the branch is already known fully
   invalid via the guaranteed zone alone.


9. STATE-SPACE PROTECTION
=====================================================

[PROVEN, and directly tested] Occupancy uncertainty introduces NO
additional combinatorial dimension at all -- `DEFAULT_MAX_ENUMERATED_
STATES` and the enumeration loop are UNCHANGED in shape from Phase 2A;
only the PER-COMBINATION occupancy factor (a closed-form product,
Section 3) was added. `total_states_considered` therefore depends only
on (number of SAFE fire branches) x 2^(number of relevant, uncertain
door/exit/stair objects) -- exactly as before, with zero contribution
from however many uncertain-occupancy zones exist.

Verified directly by `OccupancyStateSpaceProtectionTests::test_many_
independent_uncertain_occupancy_zones_do_not_explode_state_count`: 20
independent, uncertain-occupancy, unreachable zones (which, if
occupancy were naively enumerated as a Cartesian product, would be
2^20 = 1,048,576 combinations) -- `total_states_considered` is exactly
1, and `p_valid` matches the hand-derived closed-form product
(0.5^20) exactly.


10. EXACTNESS-STATUS BEHAVIOR
=====================================================

`exact` is `True` iff `unresolved_occupancy_zone_ids` is empty AND the
engineering-state enumeration completed (not skipped for size) -- the
SAME field, SAME meaning Phase 2A established, now genuinely achieved
far more often: FixedValue, WeightedOptions, discrete UniformRange, and
continuous UniformRange occupancy distributions are ALL now resolvable
exactly (Section 8, item 2) -- the ONLY remaining "unresolved" case is
a genuinely degenerate/malformed distribution (e.g. a WeightedOptions
whose weights sum to <=0, which `sample()` itself would treat as
undefined territory).

`exact_for_analyzed_dimensions` retains its Phase 2A meaning unchanged:
`True` whenever the ANALYZED zones/dimensions were computed exactly,
regardless of any excluded, unresolved zone.

Both directions verified by dedicated tests: `ExactnessStatusTests::
test_fully_exact_when_all_relevant_uncertainty_is_covered` (a mixed
door + occupancy WeightedOptions case, confirms `exact=True`) and
`test_genuinely_unresolvable_occupancy_distribution_is_not_mislabeled_
exact` (a degenerate zero-weight-sum WeightedOptions, confirms
`exact=False` and the zone appears in `unresolved_occupancy_zone_ids`
with an explanatory warning). Also `Deterministic
CaseTests`/`test_discrete_uniform_range_occupancy_is_now_resolved_
exactly_by_phase_2b` (in the Phase 2A test file, updated -- Section 12)
directly demonstrates the Phase 2A -> Phase 2B exactness improvement
for the SAME fixture that used to be disclosed as unresolved.
