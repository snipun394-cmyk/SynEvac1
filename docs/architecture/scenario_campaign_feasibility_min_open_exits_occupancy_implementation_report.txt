2. THE PREVIOUSLY INCOMPLETE PHASE 2B BEHAVIOR
=====================================================

Phase 2B's own `_reachable_open_exit_count(graph, state_map,
guaranteed_zones)` (removed by this task, folded into the new
`_zone_reachable_open_exit_sets()`) computed `egress_ok` using ONLY the
module-level `guaranteed_zones` set (zones whose occupancy_distribution
guarantees P(zero)==0.0), never the SAFE-but-uncertain zones. When
`egress_ok` was already True from guaranteed zones alone, the result
was exact (this is precisely the shortcut this task preserves). When
`egress_ok` was False from guaranteed zones alone but a SAFE uncertain
zone's own possible presence could, if occupied, supply the missing
reachable exit(s), Phase 2B silently treated the whole combination as
"insufficient egress unless literally nobody is present" -- understating
`p_valid` (a real, disclosed-but-uncorrected false negative) whenever
such a zone existed. This never affected `exact_for_analyzed_dimensions`,
but it DID mean `exact=True` was, in that narrow case, an overclaim in
substance (though never contradicted by any test in this thread, since
no prior test constructed this specific configuration) -- Section 8
below explains why `exact=True` is now genuinely, not just nominally,
correct.


3. THE MATHEMATICAL MODEL IMPLEMENTED
=====================================================

For one fixed (fire-branch, engineering-state) combination, having
already classified every occupancy-relevant zone as UNSAFE or SAFE
(Phase 2B's own unchanged two-check classification):

  p_U = P(every UNSAFE zone is empty) -- unchanged from Phase 2B,
  still a simple product of per-zone P(zero) values. An unsafe zone's
  ONLY valid contribution is zero occupants; it is never given to the
  exit-coverage computation below, exactly matching the task's own
  explicit "an unsafe zone must never help satisfy min_open_exits"
  requirement.

  If `min_open_exits <= 0`: `P(valid | combination) = p_U` -- the
  min_open_exits dimension cannot reject anything, closed-form,
  unchanged from Phase 2B, no exit-coverage work performed at all.

  Otherwise, among the SAFE zones:
    `base_reachable` = union of reachable-open-exit sets
    (`_zone_reachable_open_exit_sets()`) over SAFE zones that are
    GUARANTEED occupied (P(zero)==0.0) -- their contribution is
    unconditional.
    `need = min_open_exits - |base_reachable|`.

  If `need <= 0`: `base_reachable` alone already meets the threshold,
  so no SAFE zone's uncertain occupancy can possibly matter to this
  condition -- `P(valid | combination) = p_U`, the exact Phase 2B
  closed-form shortcut, preserved byte-for-byte in behavior for this
  (the common) case. This is `ThresholdAlreadySatisfiedTests` in the
  new test suite.

  If `need > 0`: every SAFE zone with genuine uncertainty
  (0 < P(zero) < 1) contributes its RESIDUAL reachable-exit set
  (`R(zone) - base_reachable`) if nonempty; zones with an IDENTICAL
  residual are merged into one GROUP whose activation probability is
  `1 - product(P(zero) over the group's zones)` (Section 5). Let
  `coverage_probability = P(|union of activated groups' residuals| >=
  need)`, computed exactly by `_exit_coverage_probability_at_least()`
  (Section 4/6).

  Let `p_all_safe_empty = product(P(zero) over ALL safe zones)` --
  provably 0.0 the instant any SAFE zone is guaranteed-occupied (its
  own P(zero) factor is 0.0), so this term is a real possibility only
  when NO safe zone is forced to be present. Let `structural_ok =
  (total open exit count >= min_open_exits)` -- unchanged, the same
  unconditional STRUCTURAL rule Phase 2A already reproduces.

  `P(valid | combination) = p_U * (coverage_probability +
  (p_all_safe_empty if structural_ok else 0.0))`

  This single formula, implemented verbatim in `_combo_occupancy_factor()`,
  is a full generalization: it reduces to Phase 2B's own formula exactly
  whenever no SAFE zone has genuine uncertainty (the coverage DP then
  sees zero groups, contributing 0 whenever `need>0`, leaving only the
  `p_all_safe_empty`/`structural_ok` structural-fallback term -- which
  IS Phase 2B's own `p_safe_all_empty * structural_ok` branch, verified
  identical by inspection and by every pre-existing Phase 2A/2B test
  passing unchanged).


4. HOW UNSAFE-ZONE EMPTINESS AND min_open_exits ARE COMBINED
=====================================================

Multiplicatively, via `p_U`, exactly as Phase 2B already established
(Section 3 above) -- `p_U` is computed once per combination and applied
as an outer factor around the ENTIRE occupancy-dependent condition
(both the "every unsafe zone empty" requirement and the min_open_exits
condition are required SIMULTANEOUSLY for validity; since a candidate's
occupant placements across DIFFERENT zones are independent draws
(Phase 2B's own proof, unchanged), and unsafe zones never appear in any
SAFE-zone coverage computation, `p_U` and the coverage/structural term
are independent factors of two disjoint zone sets' own independent
occupancy events). `UnsafeAndSafeUncertainZoneJointTests` verifies this
multiplicative combination directly against a hand-derived `q * p`.


5. HOW OVERLAPPING REACHABLE-EXIT SETS ARE HANDLED
=====================================================

[PROVEN, this task, a genuine structural finding not assumed from
either prior report] Within a SINGLE fixed engineering-state
combination, two zones' own reachable-open-exit sets
(`_zone_reachable_open_exit_sets()`) can only ever be IDENTICAL (both
zones lie in the same connected "indoor" component) or DISJOINT
(different components) -- never partially overlapping-but-different.
Reason: reaching a given exit means reaching that exit's own hosting
zone; since every Edge in this graph is bidirectional
(navigation_validation.py's own documented invariant, re-confirmed),
two zones that both reach the same exit are, by that very fact, mutually
reachable from each other too, which means they lie in the SAME
connected component -- and a connected component's own total set of
reachable exits is, by definition, shared identically by every zone in
it. A real Building/Definition therefore cannot construct the classic
"{B,C} vs {C,D}" partial-overlap example end-to-end as two DISTINCT,
non-identical zone contributions under one combination.

This does not make the general union-of-sets handling unnecessary,
for two reasons: (a) the merge-by-identical-contribution step
(Section 6) still needs a correct, general mechanism even for the
"identical" case (many zones sharing one component, `Identical
ContributionMergeTests`, `LargeUncertainZoneCountStressTests`), and
(b) implementing the DP in fully general form (no identical-vs-disjoint
special-casing) is not meaningfully more complex, and keeps the module
correct if the graph model's edge-directionality assumption ever
changes. `_exit_coverage_probability_at_least()` is therefore
implemented generally, and `ExitCoverageDPUnitTests` verifies it
directly against the task's own worked `{B,C}`/`{C,D}` example and a
three-way overlap case (`{B,C}`, `{C,D}`, `{D}`, hand-enumerated over
all 8 activation patterns) at the algorithm level, proving the
implementation does NOT reduce to naively summing contribution SIZES
(which would wrongly credit the `{C,D}`-only outcome as meeting a
3-exit threshold).


6. COMPLEXITY AND STATE-SPACE BOUNDS
=====================================================

Per engineering-state combination: `_zone_reachable_open_exit_sets()`
costs exactly one `bfs_reachable()` call per OPEN exit (identical cost
to the `_reachable_open_exit_count()` function it replaces -- never one
call per zone). The coverage DP (`_exit_coverage_probability_at_least()`)
then runs over GROUPS, not zones: zones sharing an identical residual
reachable-exit set are merged into one group before the DP ever sees
them (`_combo_occupancy_factor()`'s own `contribution_groups` dict,
keyed by the residual `FrozenSet[str]`), so the DP's own state count
depends only on the number of DISTINCT residual sets and the size of
their union -- provably bounded by `2^m` where `m` is the number of
DISTINCT exits appearing among those residuals, never by the number of
underlying zones or occupants. `LargeUncertainZoneCountStressTests`
demonstrates this directly: 60 zones sharing one identical residual
collapse to exactly 1 DP group, `total_states_considered` stays 1 (not
`2^60`), and the result matches the closed-form `1 - p^60` exactly.

`total_states_considered` (the OUTER engineering-state enumeration,
`DEFAULT_MAX_ENUMERATED_STATES`) is completely UNCHANGED in shape --
occupancy uncertainty, including this extension's own exit-coverage
work, still contributes ZERO additional dimension to that count
(re-verified: every new/modified test's `total_states_considered`
equals exactly `(safe fire branches) x 2^(uncertain door/exit/stair
objects)`, with no occupancy-driven multiplication anywhere).

A SEPARATE, dedicated safety bound was added for the new DP itself:
`MAX_EXIT_COVERAGE_STATES = 4096`, checked ONCE per
`compute_exact_candidate_validity()` call (never per combination,
never mid-enumeration) against `2^(total Exit edges in the Building)`
-- a purely structural, combo-invariant upper bound on any single
combination's own exit-coverage state space (real state counts stay far
below this in practice, since grouping collapses identical
contributions first; this is a hard safety ceiling for the pathological
case of many, many DISTINCT exit subsets, kept entirely separate from
`DEFAULT_MAX_ENUMERATED_STATES` so neither limit silently absorbs the
other's budget). The check is skipped entirely (zero overhead) whenever
`min_open_exits <= 0` or no zone has genuine occupancy uncertainty --
preserving every existing fast path. When exceeded, the function
returns immediately (`state_space_too_large=True`, `exact=False`,
`p_valid=None`) BEFORE any enumeration begins -- never a partial or
approximated result. Verified directly by
`ExitCoverageStateSpaceProtectionTests`, which monkeypatches
`MAX_EXIT_COVERAGE_STATES` down to 1 on an otherwise-normal 2-exit
fixture and confirms the honest "too large" result, not a silently
wrong or estimated one.


7. SHORTCUTS / PRUNING USED
=====================================================

- The `need <= 0` shortcut (Section 3): whenever guaranteed-occupied
  SAFE zones alone already meet `min_open_exits`, no coverage DP runs
  at all -- `ThresholdAlreadySatisfiedTests`.
- Redundant zones (whose residual, after subtracting `base_reachable`,
  is empty) are dropped before ever reaching the DP --
  `RedundantUncertainZonesTests` (end-to-end) and
  `ExitCoverageDPUnitTests::test_redundant_contribution_does_not_change_the_probability`
  (algorithm-level).
- Identical-contribution merging (Section 5/6) -- zones sharing one
  residual collapse to one DP group, tested at both small scale
  (`IdenticalContributionMergeTests`) and large scale
  (`LargeUncertainZoneCountStressTests`, 60 zones).
- The exit-coverage state-space bound (Section 6) is checked once,
  up front, never inside the enumeration loop.
- `DEFAULT_MAX_ENUMERATED_STATES` and Phase 2A's own LETHAL-fire-origin
  pruning and topological relevant-edge pruning are completely
  untouched -- re-verified unchanged by the full Phase 2A/2B regression
  suites passing without modification (Section 10).


8. EXACTNESS-STATUS CHANGES
=====================================================

No field, meaning, or computation path for `exact` /
`exact_for_analyzed_dimensions` was changed -- both retain their
Phase 2A/2B definitions verbatim (`exact = not unresolved_occupancy_
zone_ids` AND no engineering-state or exit-coverage enumeration skipped
for size; `exact_for_analyzed_dimensions` unchanged). What changed is
what those fields now MEAN in substance: before this task, `exact=True`
could occur in a configuration where a SAFE uncertain zone's own
occupancy genuinely could have changed the min_open_exits outcome, an
unmodeled (though disclosed-in-prose) dimension -- an overclaim in
substance if not in the field's own literal definition. After this
task, every randomness dimension this module claims to analyze
(fire origin, door/exit/stair state, min_open_exits INCLUDING its
occupancy interaction, and every zone's own occupancy uncertainty) is
either computed exactly or explicitly disclosed as unresolved/too-large
via `unresolved_occupancy_zone_ids` or `state_space_too_large` --
`exact=True` is now genuinely, provably exact for every dimension this
module claims to cover, not merely nominally so. No currently-supported
randomness affecting NAVIGATION-scoped candidate validity remains
unmodeled; the five non-NAVIGATION validator categories remain the
same, already-disclosed, deliberately out-of-scope exclusion carried
over unchanged from Phase 2A/2B.
